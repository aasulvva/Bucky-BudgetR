# Bucky BudgetR

Self-hosted, envelope-style ("bucket") budgeting application.

- **Audience:** not for public use. Hosted on LAN and reachable over Tailscale. Internet exposure may be considered later, but because this is financial data, security comes first.
- **Platform:** web app, usable on desktop and mobile.

## Tech stack

| Layer    | Choice                     |
| -------- | -------------------------- |
| Frontend | React + TypeScript         |
| Backend  | Go (REST API)              |
| Database | PostgreSQL                 |
| Runtime  | Docker containers (Compose): one app container (the frontend embedded in the Go binary), PostgreSQL, Caddy for HTTPS, daily backups |

## Glossary

| Term | Meaning |
| ---- | ------- |
| **Cycle** | A budget period (usually a month, aligned to e.g. payday). |
| **Bucket** | A budget category funded from one bank account. |
| **RA** – Refill Amount | Amount budgeted into a bucket each cycle. |
| **BC** – Bucket Capacity | Max funds a bucket can normally hold. |
| **TF** – Target Funds | What the bucket *should* have (sum of its bucket transactions). |
| **CAF** – Current Available Funds | What the bucket *actually* has, after the Money Allocation Routine. |
| **OVF** | Overflow – money removed from a bucket at cycle change. |
| **Savings target** | A Fully manual bucket or a savings, BSU, fund or investment account with a goal (§8). |
| **Held funds** | Money reserved in its source account for a savings target until it's moved there (§8). |

## 1. Users

| Field | Notes |
| ----- | ----- |
| User-ID | 6-digit random number |
| Username | unique |
| Password | bcrypt hash |
| Active | bool |
| Admin | bool |
| Preferences | JSON: default refill mode and negative TF handling for new buckets, income rules for *On income* refills (§6), locale (number and date format), language (English, Norwegian bokmål or nynorsk; follows the locale by default), time zone, cycle rule (§3) |
| Created / Modified, Created by | audit |

**Initial setup:** on first start a default admin account is created with password `BuckyBudgetR_ADMIN_Pa$$w0rd`. The user must change it at first login. The default can be overridden with an environment variable.

**User management (admins):** admins create users, activate and deactivate them, grant and revoke admin, and reset passwords. A new or reset user gets in with what the admin picks, shown to the admin once: a **link** (the default) where they choose their own password and are logged in, which works once for 24 hours; or a generated **temporary password**, which they must change at their next login. A new link or password voids the old link, and a reset ends the old password and sessions at once. Users are never deleted: deactivating blocks login and ends their sessions, and keeps their data. Admins manage accounts only, never other users' money. An admin can't change their own account there (they use Settings), and the last active admin can't be demoted or deactivated.

**Logs (admins, #93):** the app keeps, besides its stdout log, the entries that matter for troubleshooting in the database: **warnings and errors** (with the request, the user, and a panic's stack trace), **app events** (startup, migrations, ready, shutdown, cycles started and ended, scheduled transactions recorded or queued), and **admin actions** (users created, activated or deactivated, admin granted or removed, passwords reset, the retention changed), each with who did it and to whom. Ordinary requests are only in the stdout log. Entries never hold passwords, links, tokens or amounts. Events are kept 30 days, warnings and errors 90 and admin actions 365 by default; admins change that on the Logs screen (1–3650 days each), and older entries are deleted within the hour. An error shows its request ID as a **reference** to copy and pass on; for admins it opens that request's entries.

**Recovery:** when no admin can log in, `bucky-server reset-password --user <name>` on the server (`docker compose exec app …` in production) gives that user a temporary password (printed), makes them an active admin and ends their sessions.

## 2. Bank accounts

| Field | Notes |
| ----- | ----- |
| Account-ID | 4-digit random number |
| Owner | user |
| Name | unique per user (ignoring case) among accounts that aren't deleted |
| Currency | ISO 4217 code, e.g. NOK. Only real currencies with at most 2 decimals (not gold, test codes or e.g. KWD). Set when the account is created and can't be changed. |
| Account type | usage, savings, BSU, fund/ASK, investment, credit card (§2.2) |
| Expected income | optional, ≥ 0: the income expected on the account per cycle, which Budget setup compares the refill amounts with (§9). Not on a credit card |
| Bank | optional, up to 100 characters (#70): the bank the account is in. *Register interest* uses it as the counterparty |
| Deleted | soft-delete flag |
| Created / Modified | audit |

**Rules**
- The balance is never stored. It is calculated from bank transactions. A balance at a point in time counts the transactions dated before it.
- **Snapshots:** to keep this fast, pre-calculate the balance at fixed points (e.g. 1 January each year) and add only the transactions after that point. Bucket TF uses the same mechanism.
- New accounts get an **Opening Balance (OPB)** transaction.
- The balance can be corrected from the Accounts screen, which creates a **Balance Adjustment (BLA)** for the difference between the entered balance and the balance at that moment.
- **Deleting** an account settles it first, all in one step. Money left in it is **transferred (TRF)** to another account or **adjusted to 0 (BLA)**, as the user chooses. Every bucket funded from it gets a **new source account** or is **deleted with it** (#137). A deleted bucket's remaining TF is released first (a BUA to 0, as when deleting a bucket, §4), so that money is part of what's transferred or adjusted; this needs an active cycle unless its TF is already 0. Money and buckets only move to an account in the same currency. Savings held on the account, for any target, are released (SVC), and if the account is a savings target itself, the target goes too and its held funds are released (§8). Card debt held on it moves with the transfer, or is released (§2.2). The account's transactions are kept.
- **Changing the type** of an account that is a savings target to one that can't be (usage) deletes the target and releases its held funds (§8).

### 2.1 BSU accounts
A **BSU** (Boligsparing for ungdom, #214) is a Norwegian housing-savings account with a limit on what may be deposited each calendar year and in all.
- **NOK only:** a BSU account is in NOK (400 `bsu_currency` otherwise, also when changing another account's type to BSU).
- **Deposits** are incomes (INC) and transfers (TRF) into the account. Interest (an income tagged *interest*, #70), the opening balance (OPB) and balance adjustments (BLA) aren't. Each transaction counts with its corrections, on its original date, so a reversed one counts as nothing. **Withdrawals** are expenses (EXP) and transfers out; they don't lower what's deposited. Years are calendar years in Norwegian time (Europe/Oslo), whatever the user's time zone.
- **Limits** are rules admins set (`/admin/bsu-rules`), since the law changes: each has the year it applies from, a yearly limit and a total limit (at least the yearly one). A year uses the rule with the latest from-year at or before it, years before them all the first one. There's always at least one rule; the first is 2021: 27 500 a year and 300 000 in all (Skatteetaten). Changes are audit-logged (`bsu.rule_changed`, `bsu.rule_deleted`); users aren't notified. Age limits and the tax deduction are out of scope.
- **Warn, then allow:** creating, correcting or moving a transaction that takes a BSU account over the yearly or total limit of its year gets 409 `bsu_over_limit` (with what may still be deposited), and one that takes money out, or more than before, 409 `bsu_withdrawal`, unless it says `bsu_confirmed`. Scheduled transactions record without asking; the *BSU over its limit* and *BSU withdrawal* notifications tell of them (§9). Each account's status (`bsu` on the account: this year's and all deposits, what's left of each, and whether it's over) shows how much room is left.
- **History setup:** the app may not know a BSU's real history (its opening date and balance in the app may be wrong), so each BSU account is set up once (`POST /accounts/{id}/bsu-history`): the year it was opened, then each year from then to now with its deposits, interest and withdrawals as the bank shows them, and today's balance. `GET /accounts/{id}/bsu-history` gives what the app has recorded per year (each amount's minimum) and the latest year it can have been opened (its first transaction's). The setup is one step, all or nothing: the opening balances become 0, each year gets what the app is missing (a deposit INC, an interest INC tagged *interest* from the account's bank, or *Interest* without one, as *Register interest* records it, and a withdrawal EXP, described *BSU history <year>* and dated 31 Dec 12:00 Norwegian time, or now this year), and a BLA makes the balance today's. After it, the history changes with ordinary corrections.
- **As a savings target** (#236), a BSU is never given more than it may still take this year (§8.1).
- **Locked until set up:** every BSU account starts locked: the ones from before #214, a new one, and one changed to BSU (changing the type to or from BSU clears the setup). A new BSU can say it was opened this year with nothing before. A BSU in another currency from before #214 stays locked; change its type or delete it. While locked (409 `bsu_locked`): no transaction can be created, corrected, reversed or moved with the account (also as the target of a move, the approval of a queued one, and the destination of a deleted account's money), and no balance adjustment; its schedules' occurrences go to the queue as invalid, with the reason; and as a savings target it's paused: the distributor, overflow and the savings budget pass it by (its share stays with the distributor), and *Done* is refused. The setup itself records while locked, and deleting the account still works.

### 2.2 Credit cards
A **credit card** (#260, the first step of #39) is an account that owes money: its balance is below 0 while something is owed, and the bank sends a bill for it each month. Purchases on it are expenses (EXP) and payments to it transfers (TRF). Its debt is set aside on the accounts that budgeted it (#261, below). The bill and *Pay bill* (#262), and interest and fees (#263) come later.

| Field | Notes |
| ----- | ----- |
| Default account | optional: where card debt no bucket budgeted is set aside (#261), and what the bill is paid from (#262), unless chosen otherwise. A usage or savings account in the card's currency. Deleting it, or changing its type to one that can't be one, just clears it |
| Credit limit | > 0 |
| Statement day | the day of the month the bill is made, 1–28 or the last day (31): it covers the debt as of the end of the day before |
| Due day | the day of the month the bill is due, 1–28 or the last day (31): the next due day after the statement day |
| Minimum payment | > 0, a fixed amount; the whole bill when that's less |

- **Created as a card:** a card is created with its fields (400 otherwise; 400 `card_default_account` for a default account that can't be one), and an account never changes type to or from credit card (400 `card_type`). Its opening balance is what's owed today, as a negative amount; one above 0 (in credit) is allowed.
- **Owed and available** (`credit_card` on the account): *owed* is −balance, at least 0; *available* is the limit plus the balance, so it's more than the limit while the card is in credit, and below 0 past the limit.
- **The limit warns, then allows:** creating, correcting or moving a transaction that takes more out of a card than it has available gets 409 `over_credit_limit` (with what's available), unless it says `limit_confirmed`. One that lowers the debt, or adds nothing to it, passes even past the limit. Scheduled transactions record without asking, and reversals, the opening balance and balance adjustments aren't checked. The *Credit limit* notification tells when a card is at 90 % of its limit or more (§9).
- **Card debt is held where it was budgeted** (#261): until the bill is paid, the money for a card's debt stays in the accounts that budgeted it, **held** there for the card, as *card debt lines* (card, account, amount; ID: the card's ID + 20 random digits) beside the bank, bucket and savings lines. What's held on an account is covered before its buckets (§7). So no single account has to pay the bill, and the money can't look free.
  - **A purchase** (EXP on a card) can take its parts from buckets on **any** account in the card's currency that isn't a card; each bucket part is held on its bucket's account, so the bucket's CAF and TF drop while the account's unallocated money stays. The rest is held on *Set aside on* (`set_aside_account_id`): the card's default account unless the purchase names another, or nowhere (null). **A refund** (INC on a card) releases the same way; a hold can go below 0 (credit), which the next purchase uses up.
  - **A cash advance** (TRF from a card) is held on the account the money went to.
  - **A payment** (TRF to a card from another account) clears the paying account's hold first. The rest of the payment releases holds on other accounts: as the user sets (`release_card_debt`, each at most what's held there), or, left out, what's held beyond what the card still owes, largest holds first. Released money is unallocated.
  - **A transfer** between other accounts carries held debt along only when asked (`carry_card_debt`, per card, at most what's held and the amount).
  - **Set aside / Release** (`POST /accounts/{card}/card-debt/set-aside`, `…/release`): debt that isn't held anywhere (a card's opening debt, debt from before this, purchases set aside nowhere) can be held on an account out of its unallocated money (a **CDH**; at most what isn't set aside, 400, and what's unallocated, 409 `not_enough_unallocated`), and held debt released (a **CDR**; at most what's held, 409 `not_enough_held`). They can be reversed, not corrected; taking a hold back needs it still held, holding again needs the money still unallocated.
  - **Corrections** keep where the rest is set aside and what a transfer carries unless told; a payment keeps its releases while its amount and accounts stay, else releases anew. Moving a transaction records it again as new. A reversal takes its card debt lines back too.
  - On the account: `card_holds` (what's held per card) and `card_debt_uncovered`; on the card: `held_on`, `set_aside` and `not_set_aside` (what's owed beyond what's held, at least 0). Holds count only for live cards.
- **No money of its own:** a card can't fund a bucket (also not as the new source of a deleted account's buckets) or hold savings: no *Add to savings*, savings budget entry or distributor money from it (400 `card_source`). It's never a savings target.
- **Deleting a card** that owes money settles it as any account (§2): a transfer from another account pays it off, or a balance adjustment sets it to 0. What was held for it stops counting. **Deleting an account that holds card debt:** the debt follows the money: a transfer to an account that isn't a card carries it there, otherwise it's released (a CDR).

## 3. Cycles

A budget period. Usually a month, but its start and end dates can be set freely, e.g. to match payday.

| Field | Notes |
| ----- | ----- |
| Cycle-ID | `<6-digit User-ID><6-digit random>` |
| Owner | user |
| Start | the moment the cycle starts, stored in UTC |
| End | the moment the cycle ends (exclusive), stored in UTC |
| State | future / active / finished |
| Generated | planned by the cycle rule, and not moved by hand since |

**Rules**
- Cycles apply to the whole user. A user has **at most one active cycle**.
- The user picks start and end **dates**. They are stored as the UTC moments of local midnight: a cycle from 01.11 to 30.11 in Oslo runs from 31.10 23:00 UTC up to 30.11 23:00 UTC.
- A user's cycles **never overlap**. One may start exactly where another ends.
- If no cycle is active, the user is prompted to start the next planned cycle or create one. Only the earliest planned cycle can be started. Started before its planned start, it starts now; otherwise it keeps its planned start.
- Cycles are **ended manually**, and **end on their intended dates**:
  - Once the active cycle's planned end has passed, bucket transactions are refused until the user **extends** the cycle (moves its end later) or **ends** it. Ended late, it keeps its planned end.
  - Ended **early**, it ends now. If the next planned cycle begins later, the user chooses to **start it now** (its start moves to where the ended cycle ended) or to **leave a gap**. In a gap there is no active cycle, so transactions can't have bucket lines; the UI says so.
  - A next planned cycle that begins where the ended one ended starts automatically.
- Extending the active cycle pushes the next planned cycle's start along if they would overlap. Planned cycles it covers completely (ending on or before the new end) are deleted, since they haven't started, and the extend dialog lists them first (#158); with a cycle rule, more are then planned. The active cycle's start can't change, and its end can't move before now or before its last bucket transaction.
- Future cycles can be planned, edited and deleted in advance. Finished cycles are read-only.
- Ending a cycle runs the **cycle-end routine**, then the **cycle-start routine** of the cycle that starts (see §6).

**Cycle rule** (optional, in the preferences; #72)
- Plans cycles automatically, e.g. from payday: a **day of the month** (1–31; a day the month doesn't have is its last day), moved to the **previous working day** (default), the **next working day**, or **not moved** when it's a weekend or a holiday. The **holidays** are none (weekends only) or **Norwegian bank holidays**: the public holidays, Easter-based ones included, plus 24 and 31 December.
- Each planned cycle runs from one of the rule's dates up to the next, at local midnight in the user's **time zone** (a preference, set to the browser's zone the first time). The cycles are adjacent, so the next one starts by itself when the active one ends on time.
- The rule keeps **N cycles planned** (1–12, default 3). It tops up when a cycle starts or ends, hourly, and when the rule changes. New cycles go after the latest cycle, on the first of the rule's dates on or after its end (and not before today's period), so there may be a gap until then. It never touches the active or finished cycles, or planned cycles the user made or moved.
- Changing the rule (or the time zone) replans the generated cycles that haven't started. Turning it off keeps the planned cycles. A deleted planned cycle is planned again; to plan fewer, lower N.
- *Plan a cycle* and the start prompt suggest the rule's dates.

## 4. Buckets

| Field | Notes |
| ----- | ----- |
| Bucket-ID | `<6-digit User-ID><4-digit random>` |
| Owner | user |
| Name | |
| Source bank account | must be owned by the same user. The bucket uses this account's currency. |
| RA | Refill Amount (0 for a *Fully manual* bucket) |
| BC setting | *Multiplier* (BC = RA × multiplier, multiplier ≥ 1.00) or *Fixed amount*; a *Fully manual* bucket has *Fixed amount* or *No cap* |
| BC multiplier / BC fixed amount | per BC setting |
| TF | derived from bucket transactions |
| CAF | stored result of the Money Allocation Routine |
| Keep funds | bool – roll leftover funds over to the next cycle. If enabled, BC should normally be higher than RA so leftovers have room to roll over. |
| Negative TF | *Carry as debt* (default) / *Clear on refill* – what the refill does with an overspend (§6). Only used with Keep funds; new buckets get the user's default (preferences). |
| Refill mode | *Auto* (at cycle start) / *Manual* (button, once per cycle) / *On income* (when an income triggers it, see §6) / *Fully manual* (never refilled; #76) |
| Overflow destination | *Unallocated* / *Savings distribution* / *Specific savings target* |
| Priority | bool – funded before non-priority buckets (housing, transport, groceries…) |
| Importance | 1–10, weight in the allocation routine |
| Refilled | derived: whether the bucket has been refilled in the active cycle (§6) |
| Deleted | soft-delete flag |
| Created / Modified | audit |

**Rules**
- RA can never be above BC. With a fixed BC, BC is raised automatically when RA exceeds it.
- New buckets get an **Opening Funds (OPF)** transaction when the opening funds aren't 0. Like every bucket transaction, it needs an active cycle.
- The source account can only change to an account in the same currency, since TF is an amount in that currency. CAF is reset to 0 and the allocation routine funds the bucket from the new account.
- **Deleting** a bucket releases its remaining TF with a **BUA** to 0, so the money becomes unallocated in the source account (a negative TF is brought up to 0 the same way). That needs an active cycle unless TF is already 0. If the bucket is a savings target, the target goes too and its held funds are released (SVC, §8). The bucket's transactions stay.
- The new user preference only sets the *default* refill mode. Each bucket decides for itself.
- A **Fully manual** bucket (#76) is never refilled. It has no RA (always 0), Keep funds is always on, and its BC is a fixed amount or none. Its funds only change by hand: *Add funds* and *Remove funds* on the Buckets screen (§9), which are *This cycle only* adjustments (BUA) from or to the source account's unallocated money, and moves to or from other buckets (TF only, BAT). Adding, or a move into it, can't take TF above a fixed BC; removing stops at 0; adding may take more than the account has unallocated, which leaves the account short. Switching a bucket to it sets RA to 0 and turns Keep funds on, keeping TF; switching back asks for an RA and a BC again, and deletes its savings target if it has one, releasing the held funds (§8).
- **Overflow destination** (§8.5, #233): *Unallocated* (the default: the money stays in the source account as unallocated), *Savings distribution* (held for the distributor) or *Specific savings target* (a live target in the bucket's currency, not the bucket itself; held for it). A *Fully manual* bucket never overflows, so it's always *Unallocated*, and switching to it resets the destination. A target that goes away sends its buckets' overflow to the distributor.

**Figures per cycle** (Buckets screen, "used X of Y"). Calculated from bucket lines, never stored:
- **Start:** TF when the cycle began, the sum of the bucket's lines in earlier cycles.
- **Budget:** start + this cycle's lines except EXP and OVF (REF, INC, OPF, BUA, BAT; reductions count negative).
- **Used:** the cycle's EXP lines, net of corrections.
- **Overflow:** the cycle's OVF lines, at cycle end or when a refill pushes TF above BC.
- **Left:** budget − used − overflow. This is TF at the end of the cycle (the current TF while the cycle is active).

A finished cycle keeps its figures: lines from later cycles don't change them.

`GET /cycles/{id}/bucket-figures` returns these per bucket, with the budget split into its parts (start, refills, income, opening funds, adjustments, transfers). The Buckets screen shows the parts that aren't 0 as a breakdown: "Start 500.00 + refill 1 500.00".

## 5. Transactions

Every transaction has a **header**. Each affected bank account or bucket gets its own **line** (bank transaction / bucket transaction) linked to that header.

Transactions are immutable. An edit creates a **correction** (e.g. 100 NOK corrected to 150 NOK creates a +50 NOK adjustment, which the UI shows as a single 150 NOK transaction). A transaction entered by mistake can be **reversed**.

- **What can be corrected:** INC, EXP and TRF, and the system types OPB and BLA. REF, OVF, OPF, BUA and BAT can't: the routines and Bucket setup own them. The savings types SVR, SVC and SVB can't be corrected but can be reversed (§8). A reversed transaction can't be corrected or reversed again.
- **A transfer that took held savings off hold** (*Done*, §8) keeps its amount and accounts: only its counterparty, description and tags can be corrected (409 `savings_transfer`). Reversing it puts the money back on hold.
- **What a correction changes:** amounts, bucket lines, counterparty, description and tags. Its lines hold the difference and keep the original time. Every correction carries the counterparty, description and tags, so the newest one's are the effective values; a change of only these is a correction without lines. A move brings the description to the new transaction, and a reversal keeps it.
- **Another account:** moving an INC, EXP or TRF to another account reverses it and records it again on the new account at the original time. The new transaction *replaces* the old one, and both point to each other.

Only **INC, EXP, TRF and INP** can be created from the *Create transaction* screen.

### 5.5 Rules
- A bucket line belongs to the **active cycle** of the bucket's owner, and the transaction time must fall inside that cycle.
- **Corrections and reversals that affect buckets are only allowed inside the active cycle.** Once a cycle is finished, its bucket lines are locked. The bank amount, counterparty and tags can still be corrected, as long as the bucket lines still fit within the amount.
- An Internal Payment can only be created by the payer. Users cannot "request" money from other users.
- **Signs:** INC lines are positive and EXP lines negative, on both bank and bucket lines. The user enters positive amounts; the type gives the sign. A TRF's two lines mirror each other.
- **Bucket lines on INC/EXP:** each bucket must be funded from the transaction's bank account (this may change with cash support, #60); on a credit card, from any account in its currency (§2.2). Together they can't exceed the bank amount; the remainder simply isn't tied to a bucket.
- **TRF** goes between two of the user's accounts in the same currency. Transfers between currencies come with multi-currency (#33).
- **BSU accounts:** a deposit over the limits, or a withdrawal, needs confirming (§2.1).
- **Credit cards:** a purchase past the credit limit needs confirming (§2.2).
- **No future dates:** a transaction records what has happened, so its time can't be later than now. Planned payments are scheduled transactions (#31).
- **Reading:** the transaction list shows each transaction merged with its corrections (effective amounts, flagged as corrected or reversed); a reversed one also carries its amounts from just before the reversal (`before_reversal`), so the list can still show what it was. A transaction's history shows the original and each correction.
- **Suggestions:** `GET /tags` lists the user's tags, most recently used first. `GET /counterparties` lists the counterparties of incomes and expenses, each once (ignoring case), newest first, with the effective account, tags and buckets of its newest transaction that isn't reversed.
- **Math:** calculate with full precision. Stored amounts use 2 decimals, rounded half away from zero (0.005 → 0.01, −0.005 → −0.01). Exchange rates use 8 decimals.

### 5.6 Scheduled transactions

A **schedule** records an INC, EXP or TRF later, once or again and again (#31). It holds the transaction as *Create transaction* would (account, amount, counterparty, description, tags, bucket lines) and when to record it. Each transaction it records gets its description; *Make recurring* copies the transaction's.

| Field | Notes |
| ----- | ----- |
| Schedule-ID | `<6-digit User-ID><4-digit random>` (10 digits) |
| Repeat | once, or every N days, weeks, months or years from a start date |
| Time | a time of day in a time zone (the user's when it's created), so it stays at the same local time across DST |
| End | never, after N occurrences counted from the start date, or after the one on an end date |
| Mode | **auto** (record it when due) or **approve** (queue it a number of days before its time, due then, #155) |
| Paused | a paused schedule records and queues nothing |

- **Monthly and yearly** keep the start date's day, using the last day of shorter months (31 Jan → 28 Feb → 31 Mar).
- **First occurrence:** the first at or after the time the schedule is created or changed. Earlier ones aren't recorded, so resuming a paused schedule skips the ones it missed. One exception (#155): a new schedule whose first time passed at most an hour ago (a time set to this minute has passed by the time it's saved) handles that one too, on the scheduler's next run.
- **When it's due,** the scheduler (a background loop) records it dated at its scheduled time, with its bucket lines in the active cycle and the usual refill rules (§6). An occurrence it can't record goes to the **approval queue** with the reason: no active cycle, its time is outside the active cycle (e.g. after the server was down), or the transaction breaks a rule (a deleted account or bucket).
- **Catching up:** after a downtime, the missed occurrences follow in order. Each occurrence is handled once.
- **Occurrence-ID:** `<10-digit Schedule-ID><8-digit random>` (18 digits). Each records its scheduled time, its state (applied, queued or skipped), why it was queued and the transaction it recorded.
- **Deleting a schedule** deletes its occurrences, queued ones too. The transactions it recorded stay.
- **Recorded at once** (#154): a transaction entered in *Create transaction* and set to repeat is saved as a schedule whose first occurrence, when it's now or past, is recorded straight away, dated then, in the same database transaction (`POST /schedules?record_first=true`); the schedule goes on from the next at or after now. If that transaction can't be recorded, nothing is saved. A first occurrence in the future is left to the schedule. A schedule that asks first records it too, since it's entered as done. *New schedule* on the Scheduled tab does the same (#155); *Make recurring* doesn't, as its first time is the transaction it started from.
- **Screens** (#154): *Transactions* has a *Scheduled* tab listing the schedules in words ("Every month on the 25th at 08:00", "Every 2 weeks on Monday at 07:00 · 3 times") with their next time (local time), *Asks first* and *Paused* badges, and a menu to edit, pause or resume, and delete (after asking). *Show paused* (on) and *Show ended* (off) filter the list, remembered in the browser, with a count of the hidden ones. The schedule form is the *Create transaction* form with a *Repeat* section (start date and time, repeats, ends, record or ask first with the due period, name, and paused when editing) and a preview of the next five times from `POST /schedules/preview`. It opens from *New schedule* on the tab, from *Repeat or schedule* in *Create transaction*, and from *Make recurring* on a transaction (which starts like it, from its time, monthly, so it goes on from the next). A schedule's bucket lines don't need an active cycle until they're recorded.
- **A future date** (#154): a transaction in *Create transaction* dated later than now is saved as a schedule for that time, once, without `record_first`; the form says so and offers *Record it* or *Ask me first* (with the due period). The date field no longer stops at now.
- **Marked transactions:** a transaction a schedule recorded has `schedule_id` (null once the schedule is deleted). The list marks it with a repeat icon, and its detail links to the schedule.
- **Approval queue** (#155): queued occurrences wait at the top of the *Scheduled* tab, overdue ones first, then the oldest. Each shows its schedule's title and amount, its scheduled time (local time), why it waits (*Asks for approval*, *There was no active cycle*, *Its time was outside the active cycle*, or *It couldn't be recorded* with the rule it broke) and a *Due 11 Nov* or red *Overdue* badge. An *Ask me first* occurrence is queued its schedule's number of days (*Ask days before*, 0–60, 3 by default) before its time, so it can be approved early, for example rent paid before the 1st. Its due time (`due_at`) is its scheduled time, and it's **overdue** once that has passed on the business clock (the API sends it as `overdue`). One queued because it couldn't be recorded is due at its time too, so it's overdue at once.
  - **Approve** records the schedule's transaction as it is (`POST /scheduled-transactions/{id}/approve` with no body). **Edit and approve** opens the *Create transaction* form filled in from the schedule, with the type fixed and no repeat, and *Approve* sends the edited transaction as the body. **Skip** (`…/skip`) marks it skipped; it's never recorded.
  - **The approved date:** its scheduled time if that has passed and the active cycle contains it, else now (so one approved early is dated then). *Edit and approve* starts there and lets it change, up to now.
  - Approving records the transaction under the same rules as *Create transaction*: one that can't be recorded (no active cycle, outside the cycle, a deleted account or bucket) saves nothing and stays queued, with the error. One that's already approved or skipped is `409 already_resolved`.
  - **Several at once:** checkboxes (and *Select all*) select occurrences to *Approve selected* or *Skip selected*, as they are. They're sent one at a time in the queue's order, the ones that fail stay selected, and a note says how many failed and why.
  - **Counts:** while anything waits, the *Scheduled* tab and *Transactions* in the side menu show the number, and the mobile bottom tab shows it on its icon, red when one is overdue. The queue is fetched again every minute. It also shows under Notifications (#57, §9).
- **Coming up:** `GET /upcoming-transactions?count=n` (1–50, 5 by default) lists the next times of the schedules that aren't paused or ended, merged and earliest first.

## 6. Cycle routines

The routines run in the same database transaction as ending or starting the cycle, so they happen exactly once.

### Cycle end
1. Check that CAF fits the accounts (§7), so the funded part is known. This doesn't reallocate otherwise.
2. For each bucket with **Keep funds off** (so never a *Fully manual* one), an **OVF** transaction brings a positive TF to 0. Only the funded part (CAF) is real money for the overflow destination; the unfunded rest simply disappears. A negative TF stays until the next refill.
3. The OVF is dated now, or just before the cycle's end if it is ended late, so it belongs to the ending cycle.

### Cycle start / refill
A refill happens according to each bucket's **refill mode**:
- **Auto:** at cycle start, dated at the cycle's start.
- **Manual:** via a button on the Buckets screen (`POST /buckets/{id}/refill`), dated now. Only buckets with this mode.
- **Fully manual:** never. Such a bucket isn't refilled when created either, and opening funds don't count as a refill (§4).
- **On income:** when an income (INC) triggers it. It refills every *On income* bucket funded from the income's account that hasn't been refilled in this cycle, dated at the income's time. An income triggers it when:
  - its **"Triggers refill"** flag is set (the UI pre-checks it when the account has *On income* buckets left to refill, or a rule matches), or
  - the flag isn't given and one of the user's **income rules** (preferences) matches: the same counterparty, ignoring case, and an amount of at least the rule's minimum (e.g. the employer, ≥ 20 000). An explicit flag overrides the rules.

  The income must fall inside the active cycle; an explicit flag on an income outside it is refused. The flag can also be set or cleared later with a correction. **Reversing** the income (or moving it to another account) undoes its refills: their REF and OVF are reversed and the buckets can be refilled again. An OVF's savings come back the way they went, as far as the money is still there (§8.5). Refills in a finished cycle stay.

- **New bucket:** a bucket created while a cycle is running can be refilled at once (`refill` on `POST /buckets`, Bucket setup's *Refill now*), dated now, whatever its mode. Creating it with **opening funds** (OPF) instead also counts as its refill for that cycle, so no later refill in the cycle changes the amount. *Start at 0* leaves it to its refill mode: a *Manual* or *On income* bucket can still be refilled in the cycle, an *Auto* one waits for the next cycle's start.

A bucket is refilled **at most once per cycle** (tracked per bucket and cycle). The REF amount depends on Keep funds:
- **Keep funds off:** TF is set to RA, so REF = RA − current TF (a negative TF is cleared).
- **Keep funds on:** RA is added to TF. If the new TF is above BC, the excess is removed with an **OVF** transaction and sent to the overflow destination. A negative TF depends on the bucket's *Negative TF* option:
  - **Carry as debt** (default): RA is added as usual, so the overspend is paid back from the refill (TF −300, RA 4 000 → TF 3 700).
  - **Clear on refill:** TF is set to RA, as without Keep funds, with one REF of RA − TF (TF −300, RA 4 000 → REF 4 300, TF 4 000). Undoing the refill brings the debt back.

  The debt is only cleared at a refill: a bucket that isn't refilled in a cycle keeps it.

A REF or OVF of 0 isn't recorded, but the refill still counts.

The **savings budget** (§8.6) runs right after the refills of the same moment: its *At cycle start* entries after the Auto refills, its *On income* entries after the *On income* refills of the same income (and its account's recalculation). Undoing the income undoes them too. Its **sweeps** (#235) follow: an *After the refills* sweep runs after the refill that leaves every bucket on its account refilled (all but the *Fully manual* ones, at cycle start, on income, a manual refill or a new bucket), and is undone with a refill on the account. An *At cycle end* sweep runs at the end of the cycle, after the OVFs that empty the buckets, so it sweeps what they gave back too; it runs when the cycle is ended early too, and before the next cycle's refills.

A refill raises TF without adding money, so on its own it only moves CAF when the account crosses Σ TF (§7). An income that triggers a refill is money no bucket owns, so its account is recalculated with the refilled TFs (and again when its refills are undone).

## 7. Money Allocation Routine

Funds the buckets: works out how much of each source account's money backs each bucket (CAF), based on TF.

- Runs **per source account**, per user. The buckets share the balance less the credit card debt held on the account (§2.2): card debt is covered first.
- **Enough funds** (account balance ≥ Σ TF of its buckets): CAF = TF for every bucket. The leftover is stored and displayed as *unallocated*. Later, unallocated money can optionally be passed to the savings distribution.
- **Not enough funds:**
  1. Priority buckets are funded first.
  2. The remaining funds are split by weight: `CAF_i = available × (TF_i × importance_i) / Σ(TF_j × importance_j)`. No bucket gets more than its TF, and any excess is split again among the rest. If even the priority buckets can't be fully funded, the same split is used among them.
- Buckets with TF ≤ 0 get CAF = 0. A negative account balance counts as 0 available.
- **Rounding:** shares are calculated at full precision, rounded down to cents, and the leftover cents go one each to the buckets with the largest remainders, so the CAFs add up to exactly what was split.
- CAF is **stored**, so funds aren't redistributed on every change. After every transaction, for the accounts it touched (directly or as a bucket's source):
  - **A bucket line moves its own bucket's CAF** by its amount: an expense of 50 from Groceries takes 50 of Groceries' CAF, and the other buckets keep theirs. Card debt held on an account counts as money going out of it, so a card purchase from a bucket moves that bucket's CAF the same way.
  - **Moving funds between buckets on one account (BAT) takes covered money along:** the sending bucket hands over up to the moved amount of its CAF (a gap it had stays with it), and the receiving bucket takes it up to its TF; what it can't take goes back. Between accounts, each account follows the rules below.
  - Each CAF is then kept to 0 ≤ CAF ≤ TF.
  - The account is **recalculated** only when:
    - part of the transaction's bank line isn't on a bucket: an income, expense or transfer without bucket lines, or the part of a split that isn't tied to a bucket. That is money no bucket owns, however little;
    - a bucket's CAF is spent (0 or below), or an income into an overspent bucket leaves its CAF above TF;
    - the balance crosses Σ TF of the account's buckets, up or down (a refill can do that);
    - CAF no longer fits (Σ CAF above the balance), or the balance covers Σ TF but CAF doesn't match it.
  - Otherwise nothing moves, so an underfunded account can leave a refilled bucket uncovered. **Reallocate** on the Buckets screen (`POST /accounts/{id}/reallocate`) recalculates it by hand.
- **Bucket changes recalculate at once:** creating or deleting a bucket, moving it to another account, or changing its priority or importance recalculates the accounts involved right away.
- **Unallocated** is the account balance minus the card debt it covers, the CAF of its buckets, and the part of its savings reservations the balance covers (§8): `unallocated = balance − card covered − Σ CAF − covered`, where `card covered = clamp(balance, 0, card debt)` and `covered = clamp(balance − card covered − Σ CAF, 0, reserved)`. It is derived rather than stored. The routine itself ignores savings reservations: buckets are funded first, so when an account runs short, its reservations go uncovered before its buckets do; card debt goes uncovered last (#261).

## 8. Savings module

Savings targets and the money held for them (#231), and the distributor that splits money among them (#232). Overflow to savings (#233), a fixed amount per cycle (#234), the sweep (#235), the BSU cap (#236) and the Dashboard's *Savings* and *Savings to transfer* widgets (#237, §9 Dashboard) build on it; #35 tracks the module.

### 8.1 Savings targets

| Field | Notes |
| ----- | ----- |
| Holder-ID | `<6-digit User-ID><4-digit random>`. Savings targets and the distributor (#232) are both *savings holders*. |
| Target | a **Fully manual bucket** (§4), or a **savings, BSU, fund or investment account** (§2). Each is a target once at most. |
| Name | optional, up to 100 characters; none shows the bucket's or account's name |
| Goal | > 0: TF for a bucket, the balance for an account. A bucket's goal can't be above its fixed BC. |
| Note | optional, up to 500 characters |
| Deleted | soft-delete flag |
| Created / Modified | audit |

**Progress** is *current* (the bucket's TF or the account's balance) plus *held* (below) against the goal.

**A BSU target's room** (#236) is what it may still be given this year: the least of its yearly and total deposit limits left (§2.1), less everything held for it (whenever it was held, so money held in December and done in January already uses January's room), at least 0 (`bsu_room` on the target). The distributor, overflow and the savings budget treat it as a cap no rule passes, like a bucket's fixed BC; what doesn't fit goes to, or stays with, the distributor. Adding to savings by hand may go past it, with a note. A locked BSU (§2.1) is paused instead.

**A target goes away**, releasing its held funds in the same step (one SVC per source account) and deleting its distributor rules, when it's deleted, its bucket is deleted or stops being Fully manual, or its account is deleted or gets a type that can't be a target.

### 8.2 Held funds

Money for a target stays in its **source account**, *reserved* there until the user moves it. Savings lines record it:

| Field | Notes |
| ----- | ----- |
| Line-ID | `<10-digit Holder-ID><14-digit random>` (24 digits) |
| Holder | the target (or the distributor) the money is held for |
| Account | the source account, where it's reserved; in the target's currency |
| Amount | positive holds money, negative releases it or takes it off hold |
| Cycle | the cycle the line's time falls in, or none: savings lines don't need an active cycle |
| Created, User | audit (immutable: never modified) |

What a holder has **held** on an account is the sum of its lines there; an account's **reserved** money is the sum of all lines on it. Reservations come after buckets (§7): `covered = clamp(balance − Σ CAF, 0, reserved)` and `unallocated = balance − Σ CAF − covered`. An account short of its reservations splits what it covers among its holders by their amounts (largest remainder, as in §7); the rest is *not covered*.

### 8.3 Actions

- **Add to savings** (`POST /savings/targets/{id}/add`): holds money from an account's unallocated money, with an **SVR**. More than is unallocated is refused (409 `not_enough_unallocated`, which says how much is). For a bucket target funded from that account, the money goes straight into the bucket instead: an **SVB** with only a bucket line, which needs an active cycle and can't take TF above a fixed BC. A manual add may go past the goal.
- **Done** (`…/done`): the user has moved held money to the target. For an account target it's a **TRF** from the source account to the target account, with a savings line that takes the amount off hold; for a bucket target an **SVB** with the bucket line, the savings line, and a transfer's bank lines when the bucket is on another account (needs an active cycle containing the time, and room below a fixed BC). Part of what's held can be done, leaving the rest held. The time can't be in the future, and the amount must have been held then and still be. A transfer that takes a BSU over its deposit limits, or out of one, asks first, as a transaction does (409 `bsu_over_limit` / `bsu_withdrawal` unless `bsu_confirmed`, §2.1, #236).
- **Clear** (`…/clear`): releases held money back to unallocated, with an **SVC**.
- **Reversals:** SVR, SVC and SVB can be reversed, not corrected. Reversing an SVR is refused once its money is no longer held (moved on or released); reversing an SVC is refused unless the account has enough unallocated money to hold it again. Reversing a Done TRF or SVB puts the money back on hold.

**Figures:** an SVB's or SVD's bucket line counts as an adjustment (§4 *Figures per cycle*) and an SVB's bank lines as a transfer. SVR and SVC move no money, and an SVD's savings lines only move it between holders, so they count nowhere but in held funds and unallocated.

### 8.4 The distributor

One per user, a savings holder like the targets (#232). It's created when first set up or given money; before that it reads as *Immediately* with nothing held. Money comes in with **Add to savings** to the distributor (`POST /savings/distributor/add`, an SVR on it; later also bucket overflow #233 and the savings budget #234/#235), and it's **reserved** on its source account like any held funds.

**Rules**, per target:

| Field | Notes |
| ----- | ----- |
| Rule-ID | `<10-digit target Holder-ID><2-digit random>` (12 digits) |
| Range | from (≥ 0) up to, but not including, to (none: no end), of the target's **position**: `max(current, 0) + held`, its balance or TF plus everything held for it |
| Priority | 0–6; 0 gives the target nothing in that range |
| Past the goal | off by default: without it the target stops at its goal |

One target's ranges can't overlap (409 `rule_overlap`; touching ones are fine), and a target has at most 20 rules (409 `too_many_rules`). A target with no rule for where it stands, e.g. in a gap between two ranges, gets nothing. A bucket target never passes its fixed BC, even past the goal.

**The split** of an amount on one source account, among the live targets in that account's currency (not the account itself, if it's a target):

1. Every target with a rule for its position, a priority above 0 and room below its **limit** (the range's end, the goal unless the rule goes past it, a bucket's fixed BC, and a BSU's room this year (§8.1), whichever comes first) gets `amount × priority / Σ priorities`.
2. **In steps:** a share goes only as far as the first target reaches its limit; then the rest is split again with the rules that apply from there. E.g. 5 000 with Down payment (priority 6), Buffer at 39 500 (30 000–40 000 at 4, then 40 000 and up at 1) and Hobby (2): 1 500 first brings Buffer to 40 000 (750 · 500 · 250), then 3 500 by 6 + 1 + 2 (2 333.33 · 388.89 · 777.78, rounded once at the end: 3 083.33 · 888.89 · 1 027.78).
3. It stops when everything is placed or no target takes more; the rest **stays in the distributor**.
4. **Rounding** as in §7: shares at full precision, rounded down to cents, and the leftover cents one each to the largest remainders, never past a target's goal, BC or BSU room.

A split is one **SVD** per account: a savings line taking what's placed off the distributor, and per target a savings line holding its share there, or, for a bucket target funded from that account while a cycle is active, a bucket line putting it straight into the bucket.

**Hold modes:** *Immediately* (the default) splits as money comes in, in the same step; *At a minimum amount* splits an account's holdings once they reach the amount (checked per source account); *Manual only* waits. **Distribute now** (`POST /savings/distributor/distribute`) splits what's waiting on one account or all, whatever the mode; **Preview** (`GET /savings/distributor/preview`) shows a split without recording it. Changing the mode or the rules never moves money already held. **Clear** (`POST /savings/distributor/clear`) gives what the distributor holds back to unallocated (SVC).

**Reversing an SVD** puts the money back in the distributor (a bucket line comes out of the bucket); it's refused once a target's share has been moved on with Done or Clear.

### 8.5 Overflow to savings

A bucket's overflow (§6: at cycle end without Keep funds, or when a refill takes TF above BC) can go to savings (#233), set by its *Overflow destination* (§4).

- **Only the funded part is saved:** what the bucket's CAF covered above its new TF (`clamp(CAF − TF after, 0, overflow)`, with CAF read just before the OVF). The unfunded rest disappears as with *Unallocated*.
- **The OVF holds it** on the bucket's source account with savings lines, so it's reserved there (§8.2).
  - *Savings distribution*: one line for the distributor, which then splits by its hold mode (§8.4).
  - *Specific savings target*: a line for the target, up to its goal (unless the rule at its position has *Past the goal*), a bucket target's fixed BC and a BSU target's room this year (§8.1, #236). The rest has a line for the distributor.
  - A bucket target funded from the same account gets its share straight into the bucket: an **SVB** with the savings line and the bucket line, at the overflow's time, while the cycle holds it.
  - An account target that is the bucket's own source account already has the money, so it gets no line.
- **Undoing a refill** (reversing its income, §6) reverses the OVF: the bucket gets its funds back, and its savings come back the way they went (#234 testing). What the overflow moved on at once (the SVB straight into a bucket target, the distributor's SVD) is recorded with it and reversed first, newest first: a target gives back at most what it still holds on the account, a bucket target at most its TF, and from an SVD only the overflow's share of what it split (what the distributor already held stays split). Then each of the OVF's savings lines is taken off hold as far as its holder holds it. What was moved at the bank with Done, cleared, spent from a bucket, or held for a target deleted since stays as it is, so the account can end up short (*not covered*).
- **A target that goes away** (deleted, or its bucket or account stops being one) switches the buckets that sent their overflow to it to *Savings distribution*.

### 8.6 Savings budget

What the user saves each cycle: **fixed amounts** (#234) and **sweeps** of the money left unallocated (#235).

An **entry** (`/savings/budget`, ID `<6-digit User-ID><4-digit random>`) has a **source account**, where the money is reserved; a **destination**, a savings target in the account's currency (not the account itself) or the distributor; an **amount** per cycle; and **when** it runs:
- **At cycle start**, after the Auto refills, dated at the cycle's start.
- **On income**, after the *On income* refills that the same income triggers on its account (its *Triggers refill* flag or an income rule, §6), dated at the income's time.
- **Manually**: *Save now* (`POST /savings/budget/{id}/save-now`), dated now, in an active cycle that holds now.

Rules:
- **Once per cycle** per entry, tracked per entry and cycle like refills. A second income doesn't run it again; *Save now* a second time is 409 `already_saved`.
- **The buckets come first:** it reserves its amount with an **SVR**, or what the account has unallocated if that's less. The run still counts, and a *Savings budget short* notification says what's missing (§9).
- **The goal:** a target takes up to its goal (unless the rule at its position has *Past the goal*) and a bucket target's fixed BC; the rest is held for the distributor, on a 2nd savings line. The distributor then splits by its hold mode (§8.4), and a bucket target funded from the same account gets its share straight into the bucket (an SVB), as with overflow (§8.5).
- **Set up mid-cycle:** an *At cycle start* entry created (or switched to it) while a cycle runs reserves now (`this_cycle`, the default), or waits for the next cycle (`this_cycle: false`, recorded as a run of 0). Other entries wait for their income or *Save now*.
- **Undo:** reversing the income (or moving it to another account) reverses its entries' SVRs the way overflow is undone (§8.5): what the distributor split or a bucket target got straight in is taken back first, then the hold is released, as far as the money is still there. They can run again in the cycle.
- **Changes** to the destination, amount or *when* apply from the next run; what's reserved stays. Deleting an entry leaves what it reserved held.
- **A target that goes away** stops its entries (*stopped*): they don't run until they get another destination. **A deleted account** deletes its entries.

**Sweeps** (#235) are entries without an amount: they reserve what the account has **unallocated above an amount to keep** (`keep`, 0 by default), once per cycle, to a target or the distributor like a fixed amount. **When** is one of:
- **After the refills**, once every bucket funded from the account is refilled in the cycle, all but the *Fully manual* ones (*Manual* buckets count, so it waits for them), dated at the last refill: at cycle start, an income, a manual refill or a new bucket. An account without such buckets sweeps at cycle start. It runs after the refill's fixed amounts.
- **At cycle end**, after the OVFs of the cycle-end routine (§6), dated at the cycle's end (now when ended early). It runs before the next cycle's refills, so the amount to keep should cover them.

Rules:
- **One per mode** per account: a second *After the refills* or *At cycle end* sweep on the account is 409 `sweep_exists`. An entry can't change between a fixed amount and a sweep.
- **Nothing to sweep:** a sweep with nothing above the amount to keep still counts for the cycle (a run of 0). It's never short, so it has no notification.
- **The goal** and the distributor's split are as for a fixed amount.
- **Set up mid-cycle:** an *After the refills* sweep created (or switched to it) while a cycle runs, on an account refilled already, sweeps now (`this_cycle`, the default) or waits for the next cycle (`this_cycle: false`). On an account still waiting for a refill, it runs after it.
- **Undo:** undoing a refill on the account (reversing or moving its income) undoes its *After the refills* sweep first, as fixed amounts are undone, so it runs again once the account is refilled again.

- **Desktop:** a side menu. Dashboard and Transactions are links, New transaction is a button, and Budget & Reporting and Setup are groups that expand and collapse. Budget & Reporting and the group of the current screen start open. The profile button (avatar and username) sits at the bottom and opens the profile menu.
- **Mobile:** bottom tabs `Overview · Transactions · (+ New) · Budget · Setup`. A tab with several screens opens them in a sheet. The header shows the screen's name and the profile avatar, which opens the profile menu.
- **Version:** the app is versioned `vX.YY.ZZ`: X goes up when a milestone is done (1 = MVP), YY for a new feature, ZZ for a bugfix or minor change. The login page and the profile menu show it (with *· dev* in development). **About** shows the version, the commit it was built from and the environment (development or production). **What's New** lists every version's changes, each headed `<title> (yyyy-mm-dd) - vX.YY.ZZ`, in the app's language. It pops up when the app opens on a newer feature or major version than the user last saw (`whats_new_seen`), not after a patch, showing what changed since; closing it saves the version as seen, and *Don't show this after updates* (or the Settings switch) turns that off (`whats_new_popup`).
- **Notifications** (#57): an item above the profile button on desktop, and a bell next to the avatar on mobile, each with the number of open notifications (red when one is an alert). The count is a to-do count: opening the screen doesn't reset it. In-app only; push and e-mail are out of scope.
- The day-to-day budget screen is **Cycles**. Budget setup is part of Setup.
